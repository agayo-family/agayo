# Доставка билетов: диагностика и восстановление

После обновления открой `/admin` → «Настройки» → «Письма и повторы». Доступ требует права `manage_system`. Повтор также требует `manage_ticket_inventory` для соответствующего события.

Диагностика показывает домен отправителя, количество принятых, ошибочных и ожидающих отправок, номера билетов/заказов и безопасную причину отказа. Ключи, email покупателей и QR-токены в этот ответ не включаются. «Принято» означает ответ службы доставки, а не подтверждение попадания письма во входящие.

## Повторно отправить существующий билет

В `/admin` → «Билеты» найди заказ и нажми **«Отправить билет повторно»** (для нескольких билетов — «Отправить билеты повторно»). Одна кнопка отображается на первой видимой карточке этого заказа. Перед отправкой показываются номер заказа и исходная почта покупки.

- Кнопка доступна сотруднику с `manage_ticket_inventory` для соответствующего события, только для оплаченного заказа.
- Отправляются все действующие или использованные билеты этого заказа, даже если поиск показывает только один. Возвращённые и отменённые исключаются.
- Получатель — почта из заказа. Номер билета, QR, категория, владелец и место сохраняются. Новый заказ и новый билет не создаются.
- Эта кнопка отправляет именно email, даже если у гостя выбран Telegram. Она работает и при сохранённом статусе `sent`, потому что это явный запрос нового письма.
- После сетевого сбоя нажми **«Проверить повторную отправку»**: продолжается та же попытка, принятые билеты пропускаются. Для больших заказов за один запрос обрабатывается до шести билетов; оставшиеся продолжаются той же кнопкой. Не создавай новую попытку ради сетевого повтора.
- После успешной отправки следующее подтверждённое нажатие создаст новое письмо с теми же билетами. Между новыми попытками одного заказа действует минутный интервал.

Ответ о принятии почтовым сервисом не означает попадание во входящие. Ручной журнал сохраняет идентификаторы Resend для последующей сверки. Миграция [019](../db/019_ticket_resend_requests.sql) устанавливается заранее либо при первом явном авторизованном POST этой кнопки; простое открытие страницы её не запускает.

## Разбор причин

| Причина | Действие владельца |
|---|---|
| `test_domain` | В Resend подтвердить домен, в **Production** правильного проекта Vercel задать `EMAIL_FROM=AGAYO <tickets@agayo.ru>` и выполнить redeploy. Использовать этот адрес только после подтверждения домена. `onboarding@resend.dev` предназначен для тестов на собственную почту. |
| `unverified_domain` | Сверить точный домен EMAIL_FROM, DNS и аккаунт Resend, которому принадлежит ключ. Наличие DNS-записи само по себе не доказывает подтверждение домена в нужном аккаунте. |
| `authentication` | Сверить production-ключ и права отправки. Не публиковать ключ в чате или GitHub. |
| `daily_quota_exceeded` / `monthly_quota_exceeded` | Проверить лимит аккаунта. После сброса лимита повторить неотправленные билеты заказа. Тариф автоматически не меняется. |
| `rate_limit_exceeded` / `network` | Короткий повтор выполняется с прежним ключом. После сбоя результат остаётся в журнале доставок. |
| `invalid_idempotent_request` | Сверить прежнее письмо в Resend: с тем же ключом изменилось содержимое. Автоматически новый ключ не создаётся. |
| `idempotency_expired` / `ambiguous` | Исход предыдущей попытки неизвестен. После истечения окна Resend сначала нужна ручная сверка, чтобы исключить дубликат. |

После устранения причины нажми «Повторить неотправленные билеты заказа». Уже принятые отправки пропускаются. Новая покупка, списание денег, возврат и повторный выпуск билета не выполняются. Именное приглашение сохраняет своё описание и исходный ключ.

Если отправка принята, но письма нет, проверить в Resend статус конкретного письма: доставка, bounce, suppression, spam. Не сбрасывать `sent` массово: это может повторно отправить уже доставленные билеты.

## Фоновый повтор

Подготовлен защищённый обработчик `GET /api/cron/ticket-delivery`. Он обрабатывает до пяти оплаченных заказов за запуск, только существующие неотправленные билеты; не проверяет неоплаченные заказы и не создаёт платежей.

**Само наличие обработчика не запускает расписание.** Для работы нужно:

1. Задать отдельный случайный `CRON_SECRET` длиной не менее 32 символов в Production и выполнить redeploy.
2. Подключить существующий планировщик, вызывающий этот URL с заголовком `Authorization: Bearer <CRON_SECRET>`. Секрет не передавать в URL и не хранить в репозитории.
3. Для регулярного восстановления использовать интервал, подходящий фактическому тарифу и объёму очереди. На Vercel Hobby разрешён только ежедневный cron; частое расписание без проверки тарифа не добавляется в production-конфигурацию.
4. Проверить ответ обработчика и уменьшение очереди. Без секрета он возвращает 503, с неверным секретом — 401.

Планировщик в этом исправлении **не подключён**. До его подключения восстановление запускается webhook ЮKassa, открытой страницей проверки заказа и действием владельца в админке. Если покупатель закрыл страницу, а webhook перестал повторяться, автоматического запуска по расписанию не будет.

У Resend окно защиты ключей — 24 часа. Неоднозначные старые отправки консервативно блокируются после 23 часов от создания записи доставки; подтверждённый отказ из-за конфигурации или квоты допускает восстановление после исправления. Для обычных билетов изменение контента события между попытками может вызвать конфликт ключа — требуется сверка, а не принудительная смена ключа.

## Проверка production

Read-only проверка Neon 22.10.2026: все 19 исторических email-записей имеют `sent`, ошибок в очереди и оплаченных заказов без билетов нет. Это состояние приложения, а не доказательство конечной доставки. Подробности: [агрегаты](audit/2026-10-22-neon-production.json), [аудит](AGAYO_AUDIT_2026-10-22.md).

1. Убедиться, что нужный коммит развернут в проекте, обслуживающем `www.agayo.ru`. Репозиторий подключён к двум проектам Vercel; настройки могут отличаться.
2. Прочитать диагностику; при `sent` и отсутствии письма сверить конечный результат в Resend. Не угадывать причину по одному симптому «мне на тестах приходило».
3. Проверить журнал Resend и домен отправителя. Затем провести отдельно согласованную проверку на контролируемом внешнем ящике.
4. Проверить оплаченный заказ: статус 200, количество действующих билетов, принятые отправки и наличие письма в реальном ящике.
5. Повторить проверку заказа и убедиться, что второго письма и второго билета не появилось.

SQL для первичного чтения находится в [audit/email-delivery-diagnostics.sql](audit/email-delivery-diagnostics.sql). Он не меняет данные.

Официальные источники: [ошибки Resend](https://resend.com/docs/api-reference/errors), [тестовый отправитель](https://resend.com/docs/knowledge-base/403-error-resend-dev-domain), [идемпотентность Resend](https://resend.com/docs/dashboard/emails/idempotency-keys), [ограничения Vercel Cron](https://vercel.com/docs/cron-jobs/usage-and-pricing).
